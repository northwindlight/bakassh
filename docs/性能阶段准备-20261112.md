## 当前渲染逻辑与代价

- `TerminalView.drawFrame` 在 `NativeTerm.class` 全局锁内完成移动映射、读取脏行、光栅化和整屏位图绘制。
  `TerminalSession` 收包、输入与其他会话也使用该锁，因此需要测量跨线程 / 跨会话等待。
- 普通 `rasterizeRow` 逐格画背景、逐字形合成位图；注释提及分段不等于已经按段实现。
- `drawLiveText` 捏合期间逐帧真实字号绘制，但也持有终端锁，不能只优化静态路径。
- `applyMove` 包含多次扫描和去重；`takeMoveOps` 的 Java 容量是 128、C 累积上限为 256，截断会触发全屏回退。
  是否常见、成本多大仍待计量，不能仅凭复杂度认定主瓶颈。
- `getRow` 目前只导出格子的首码点；组合字符能力仍有限，未来快照不宜把该限制固化成新接口约定。

旧日志中约 58.6 ms 绘制 / 57.8 ms 行重建来自极密网格某区间，只是定位线索。
154×134 的 30.35 FPS 是 0.1.2 旧现场基线，不能直接视为 0.4.3 / 0.4.4 的表现。

## 本轮准备成果

1. 新增五种固定合成负载，三种网格的整包 / 切包结果逐项核对；输入和最终单元格保存 SHA-256。
2. 分包检查实际发现 UTF-8 解码器的 G0 / 非 ASCII 路径分别保留半个码点；现统一状态，并覆盖中文、四字节 emoji、DEC 制表字符和硬复位。
3. Android 新增 `local-replay` 入口，使用实际字体、JNI、TerminalView 和软件 Canvas，分别计时解析与 CPU 绘制并输出分位数 / 重建量 / 最终像素摘要。
4. 修正旧 `matched-grid` 将 FrameLayout 参数强转 LinearLayout 参数的问题；其主机选择、鉴权和清理仍未重新验收，暂不作为当前无人值守基准。

工具命令与结果边界见 [基准说明](../benchmarks/README.md)。本轮没有设备，Android CPU / GPU / 呈现和输入延迟均没有新测量结果。

离线验证：53 项主机回归、11 项 loopback SSH 回归、15 组默认固定回放通过；15 组 90 帧回放另在 UBSan 下通过。
Debug / Release / AndroidTest 编译和 lintRelease 通过（0 错误、78 条警告）。Android 测试只编译，尚未在设备执行。

## 后续实施顺序

先采集修复后基线并加分段计时，再按实际成本选择短锁快照、最终行去重、背景 / 装饰线合并。
软件行缓存仍受限时，再做硬件 Canvas 文字段 / 行指令缓存的 A/B；更大的 GPU 重写以后续证据决定。
每轮固定设备、网格、输入、字号和预热条件，核对最终画面、长尾耗时、输入积压及内存。

常用网格继续以 60 FPS 为目标；335×307 作为压力负载，不要求稳定 60 FPS。
本轮版本为 0.4.4 / code14，包含正确性修复与测试准备，不声称已经提高屏幕帧率。
